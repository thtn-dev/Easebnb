# Integration Event Infrastructure — Implementation Plan

## Survey summary (Step 0)

- Domain events: `IDomainEvent : MediatR INotification` (`BuildingBlocks.SharedKernel/IDomainEvent.cs`); dispatched by `DomainEventDispatcher` via `IPublisher`, invoked from `UnitOfWork<TDbContext>.SaveChangesInternalAsync` **before** `SaveChangesAsync`, inside the ambient EF transaction. No interceptor/middleware involved. This is ideal for the outbox: a MediatR bridge handler calling `IPublishEndpoint.Publish` during dispatch writes the outbox row atomically at save; the bus outbox only delivers to RabbitMQ after commit.
- Only one domain event exists today: `SendEmailEvent` (raised in `AuthService.RegisterAsync`, handled by a log-only `SendMailHandler`).
- One DbContext per module: `AppIdentityDbContext` (schema `identity`, snake_case via `UseSnakeCaseNamingConvention`, migrations in `Identity.Infrastructure/Database/Migrations`, manual `dotnet ef database update` from WebApi).
- Registration conventions: C# 14 `extension(IServiceCollection services)` members (`AddIdentityModule`, `AddDatabase<TDbContext>`), IOptions with `SectionName` + DataAnnotations validation, secrets via `.env` with `__` keys (DotNetEnv).
- No MassTransit/RabbitMQ/docker-compose anywhere. Health checks (`/health`, `/alive`) and OTel come from `Easebnb.ServiceDefaults`. `Modules/Organization/` is an empty solution folder.
- Existing integration tests boot the full app **without** a broker → a hard RabbitMQ dependency would break the suite.

## Design decisions

1. **PoC event**: new `UserRegisteredDomainEvent` raised additively in `AuthService.RegisterAsync` (one `user.AddDomainEvent(...)` line next to the existing `SendEmailEvent`; no refactor), mapped to `UserRegisteredIntegrationEvent`, consumed by Organization.
2. **Contracts project**: `BuildingBlocks/BuildingBlocks.IntegrationEvents` — zero package references, pure records, namespace `BuildingBlocks.IntegrationEvents`.
3. **Bridge pattern**: open-generic MediatR handler + per-mapping classes — adding a new integration event = 1 mapper class + 1 contract record, no core edits.
4. **Transport toggle** `RabbitMq:Enabled` (default `false`): when disabled, the bus uses `UsingInMemoryTransport` (no EF outbox registered) so the app and existing tests run without Docker; enabled via `.env`/appsettings when compose is up.
5. **Outbox & inbox**: per-module `AddEntityFrameworkOutbox<TDbContext>` with `UseBusOutbox()`; consumer-side idempotency uses MassTransit's built-in inbox (`mt_inbox_*` tables) — explicitly permitted by the task — plus a DB unique constraint as defense-in-depth.
6. **Per-module MassTransit registration**: each module gets `Add<Module>ModuleIntegrationEvents(cfg, configuration)` on `IBusRegistrationConfigurator`; composition root adds one line per module inside a single `AddMassTransit`.

## Implementation-order verification points

Flag and resolve while coding (each has a contained fallback): (1) MassTransit 8.5.10 availability/net10 compat; (2) whether `IBusRegistrationConfigurator` exposes `IServiceCollection` for mapper registrations (else split extension signatures); (3) bus-outbox with `AddDbContextPool` — if incompatible, switch `AddDatabase` to `AddDbContext`; (4) two `AddEntityFrameworkOutbox` registrations on one bus; (5) MT tables under module default schema + snake_case naming; (6) built-in inbox behavior on the consumer side — fallback is a base-consumer custom inbox table; (7) MassTransit auto health checks surface on `/health`.
